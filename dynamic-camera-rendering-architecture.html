Dynamic Camera — Rendering Architecture

Current Version 2 rendering rules and implementation notes

← Back to Dynamic Camera Documentation

Current Rendering Rule

The camera system now uses one rendering path for normal rendering, zooming, rotation, flipping, tile/world content, and direct background presentation. Camera effects do not select alternate renderers.

camera state → resolve scene-clamped camera center → render world / tiles / backgrounds through the normal path → apply zoom and presentation smoothing → compose ordered presentation → apply final presentation transforms such as rotation / flip
Architectural rule: alternate rendering paths should not be introduced for camera transforms. Rotation and flipping belong as late as possible in presentation, after the same camera image and layer-order work used by the normal path.

Scene-Centered Camera and Parallax

The resolved camera center is the authoritative camera position. Scene limiting clamps that resolved center itself, rather than allowing a separate requested center to continue beyond the scene edge.

sceneCenterX = sceneWidth / 2 sceneCenterY = sceneHeight / 2 cameraDeltaX = resolvedCameraCenterX - sceneCenterX cameraDeltaY = resolvedCameraCenterY - sceneCenterY

Background and parallax positioning are derived from this scene-centered relationship. At the scene center, each layer's neutral logical surface aligns with the camera/view center.

Public Camera X/Y remain the visible top-left coordinates derived from the resolved center and visible size.

Zoom-Aware Background Scroll Factor

Stencyl's stored background scroll factor remains the source setting, but bittyBIG converts it to an effective movement factor for the current visible camera size. This preserves the background's intended logical travel span while zoom changes how much of the scene is visible.

logicalSpan = baseViewportSize + baseScrollFactor × (sceneSize - baseViewportSize) effectiveScrollFactor = (logicalSpan - currentVisibleSize) / (sceneSize - currentVisibleSize)

This prevents a background that is correctly aligned at zoom 1 from drifting away from the expected scene edge at another zoom level.

Background Layer Anchor

Background positional anchoring is stored per background layer in a map. A layer with no stored value defaults to 0,0, preserving the traditional top-left registration.

ValueX meaningY meaning
0LeftTop
0.5CenterCenter
1RightBottom

Values are clamped to the range 0–1. The previous bottom-center registration is represented by X = 0.5, Y = 1.

logical anchor point = logicalSurfaceOrigin + logicalSurfaceSize × anchor image origin = logical anchor point - preparedImageSize × anchor

The anchor changes how the prepared background image is registered inside its logical parallax surface. It does not create a separate render path.

Stencyl block

Set background anchor X [0–1] Y [0–1] for Layer with [Name/ID] [...]

Translation call: scripts.api.stencyl.BittyCameraBlocks.setBackgroundLayerAnchor(anchorX, anchorY, layerLookup, layerValue);

Default: 0,0.

Repeating Background Preparation

Repeating backgrounds prepare only the minimum number of source copies required to cover their logical surface:

copies = ceil(requiredSize / sourceTileSize)

Minimum is one copy. There is no extra +1 safety copy. This avoids unnecessary prepared image area and the performance cost that came with it.

Non-repeating source images may intentionally contain overscan. Extra source width or height is treated as image coverage, not as an additional movement multiplier.

Fractional Camera Motion and Tile / World Rasterization

World and tile content is rasterized through BitmapData. Feeding a changing fractional camera origin directly into that raster caused subtle subpixel shimmer, visible even when zoom was stationary.

The renderer now separates the camera position into a pixel-aligned raster origin and a fractional remainder:

camera position → pixel-aligned raster origin → render tile/world BitmapData fractional remainder → preserve per camera → apply at final presentation wrapper

This keeps raster sampling stable while retaining smooth fractional camera movement on screen. Rasterized world layers with non-1.0 scroll factors are compensated before the shared final residual is applied so their parallax rate remains correct.

Result: the main tile/world layer no longer has the subtle settling shimmer that previously remained during ordinary camera movement or at the ends of zoom transitions.

Zoom Clamp Smoothing

The raster camera intentionally uses parity-matched integer source dimensions during smooth zoom. At a scene edge, those source dimensions change in steps while presentation zoom changes continuously.

Direct background wrappers reconstruct the smooth mathematical clamped camera center for presentation. The rasterized world presentation separately compensates for the fractional source-size remainder at the final wrapper. These corrections preserve the intentional parity-matched raster source while keeping visible motion smooth.

Rotation and Flip

Rotation no longer selects a rotation-specific capture or presentation renderer. Ordered layers, direct backgrounds, zoom behavior, scene clamping, parallax, and smoothing all run through the same normal camera path first.

normal camera render → ordered world / tile segments → direct backgrounds → zoom + clamp smoothing → normal presentation → final rotation / flip

Rotation may require enough source coverage to avoid exposing empty corners, but that coverage requirement does not change renderer ownership or layer-order behavior.

Ownership Summary

  • BittyViewports: owns resolved camera/view state, visible size, scene clamp state, and zoom state.
  • BittyRenderer: produces the world/tile raster and keeps raster sampling pixel-aligned where required.
  • BittyDisplayManager: owns presentation placement, direct background presentation, final fractional residuals, and late rotation/flip transforms.
  • BittyCameraBlocks: is the Stencyl translation/API layer and does not own rendering behavior.

Current rule: each stage does one job and hands its result forward. Camera transforms should not duplicate earlier rendering work.
