Dynamic Camera System

The bittyBIG Dynamic Camera System gives Stencyl projects a more flexible camera and output pipeline. It supports zoom, tweening, split-screen, picture-in-picture, viewport transforms, camera rotation, screenshake, and pixel-perfect display behavior.

Project Setup in Stencyl

1. Install and enable the extension

  1. Open Settings → Extensions.
  2. Install the bittyBIG Dynamic Camera System.
  3. Enable it for your project.

2. Set your normal Stencyl Screen Size

Game Settings → Settings → Display

Set Screen Size to the base game/output size you want to work with.

That’s it!

    This glossary mirrors the current Stencyl palette in the extension. Blocks are shown in palette order with their current tooltip description and Haxe call.
    

    

    Key Terms
    

    

    Screen - The full output area of the device or game window. The Game Area is positioned and sized within the Screen.
    

    Game Area - The rectangular area where bittyBIG renders the game. It can be resized and positioned anywhere on the Screen and contains the Viewports.
    

    Viewport - The output area for a single Camera. A Viewport can be positioned and sized anywhere within the Game Area.
    

    Camera - Captures a rectangular area of the Scene and renders that view to a Viewport.
    

    Scene - The Stencyl game world being viewed by the Cameras. Actors, tiles, backgrounds, and scene boundaries exist in Scene coordinates.
    

    Camera Size - The base width and height of the Scene captured by a Camera before zoom is applied.
    

    Camera Center - The Scene position at the center of the Camera's view.
    

    Camera Target - The Scene position the Camera is moving toward. This may come from an Actor, a manually specified position, or another camera-follow operation.
    

    Zoom - Changes how much of the Scene is visible through a Camera without changing its base Camera Size. Higher zoom shows a smaller area of the Scene; lower zoom shows a larger area.
    

    Scene Lock - Restricts a Camera so its visible area does not move beyond the Scene boundaries.
    

    Follow - Continuously updates a Camera's target based on an Actor.
    

    Viewport Position - The position of a Viewport within the Game Area.
    

    Viewport Size - The width and height of the Camera's output area within the Game Area. This does not change the Camera's Scene capture size.
    

    Viewport Scale Mode - Controls how the Camera image is fitted into its Viewport when their dimensions or aspect ratios differ.
    

    Game Area Coordinates - Coordinates relative to the Game Area. Viewports are positioned using Game Area coordinates.
    

    Screen Coordinates - Coordinates relative to the full Screen. The Game Area is positioned using Screen coordinates.
    

    Background Layer - A Stencyl Scene background layer rendered as part of the Camera view.
    

    Scroll Factor / Parallax - Controls how quickly a Background Layer moves relative to Camera movement.
    

    Background Repeat - Controls whether a Background Layer repeats horizontally, vertically, both, or not at all.
    

    Image Anchor - The point on a background image used when positioning that image. 0,0 is top-left, 0.5,0.5 is center, and 1,1 is bottom-right.
    

    Scene Anchor - The point in the Scene that the Background Layer's Image Anchor is aligned to.
    

    Background Offset - An additional Scene-space X/Y offset applied after the Background Layer's Image Anchor and Scene Anchor are aligned.
    

    Rendering Flow - Scene → Camera → Viewport → Game Area → Screen.

    Scene
    Setup → Scene
    

    Set Camera Scene Lock
    Locks or unlocks the camera from being limited to the scene bounds.
    Set Camera ID  Scene Lock to Lock Camera To Scene
    Code
    scripts.api.stencyl.BittyCameraBlocks.setCameraSceneLock(~,~);
    

    Set Background Layer Repeat
    Overrides Stencyl's repeat setting for this background layer in bittyBIG. If this block is not used, Stencyl's Repeat setting is preserved: off = none, on = both. Horizontal and Vertical repeat only the selected axis.
    Set repeat to None for Layer with Name 
    Code
    scripts.api.stencyl.BittyCameraBlocks.setBackgroundLayerRepeatMode(~,~,~);
    

    Set Background Layer Anchors
    Each anchor uses 0 to 1: left/top 0, center 0.5, right/bottom 1. Choose the image point and scene point independently. Background Offset adjusts the placement in scene units.
    Set background image anchor X  Y  to scene anchor X  Y  for Layer with Name 
    Code
    scripts.api.stencyl.BittyCameraBlocks.setBackgroundLayerAnchors(~,~,~,~,~,~);
    

    Set Background Layer Alignments
    Select image and scene anchor points independently. Background Offset adds a scene-unit adjustment.
    Align background image Bottom Center to scene Bottom Center for Layer with Name 
    Code
    scripts.api.stencyl.BittyCameraBlocks.setBackgroundLayerAlignments(~,~,~,~);
    

    Set Background Layer Offset
    Sets an absolute offset from the aligned background position in scene units. Positive X is right; positive Y is down. Negative Y moves up. Set 0,0 to reset. Repeated calls replace the offset; they do not add to it. Independent of scroll factor.
    Set background offset X  Y  for Layer with Name 
    Code
    scripts.api.stencyl.BittyCameraBlocks.setBackgroundLayerOffset(~,~,~,~);

Camera Size vs. Viewport Size vs. Game Area

    

    Camera Size controls how much of the Scene the Camera captures before zoom. Viewport Size controls how large that Camera output is drawn inside the Game Area. Game Area is the rectangle on the Screen that contains the Viewports. Changing one does not automatically change the other two.
    

    

    

    
Follow Actor

    

    Follow Actor is a convenience block for continuous camera tracking. You call it once, and bittyBIG keeps updating that Camera's target to the Actor every frame. Functionally, it saves you from putting Set Camera Target Center in an Update event and feeding it the Actor's position yourself.
    

    

    

    
Split-Screen Layout

    

    Each Camera starts with a matching default Viewport, so custom split-screen comes down to arranging those Viewports inside the Game Area. Resize and reposition each Viewport to the region it should occupy. Camera ID 0 starts routed to Viewport ID 0, Camera ID 1 to Viewport ID 1, and so on unless you deliberately change the routing.
    

    

    

    
Final Output Scaling / Fullscreen

    

    There are two separate scaling stages to check. Viewport Scale Mode controls how a Camera image is drawn inside its Viewport. Stencyl's own Fullscreen / Scale to Fit / Letterbox behavior can still scale the final game output after bittyBIG has composed it. If the Viewport itself looks correct but the whole game changes when entering fullscreen, check Stencyl's display/fullscreen settings rather than the Viewport Scale Mode.
    

    

    

    
Background Image Scaling

    

    Background images have their own scale-mode controls. Set the appropriate Background Image Scale Mode for the Viewport or whole Display instead of changing Camera Size to compensate for an image-layout problem.
    

    

    

    
Scene Background Layer Anchoring

    

    Use Set Background Layer Alignments for named image-to-scene alignment, or Set Background Layer Anchors for custom normalized anchors. Image and scene anchors are independent: X and Y use values from 0 to 1, where 0 is left/top, 0.5 is center, and 1 is right/bottom. Use Set Background Layer Offset for an additional scene-unit adjustment after alignment.
    

    

    

    
Debugging Camera State

    

    

    Debug Camera 0
    

    

    Use the Debug tab. Debug Camera, Debug Viewport, Debug Display, and Debug Camera System print readable multi-line reports showing the current state instead of making you inspect a pile of individual getters.

    Development Trail
    

    

    
	The Dynamic Camera System started with a simple practical problem: remove camera jitter from Stencyl projects while keeping the normal Stencyl workflow intact. My larger goal is to help put Stencyl on the map by proving it can power a polished, modern-feeling hit game when paired with the right tools.

    

    
	Over time, that small fix grew into a full rendering and camera control pipeline.

    

    
	The project still keeps Stencyl as the editor with the familiar block system, actor workflow, scene setup tool, and asset pipeline. 

    

    
	Version 1.0 is the first release-ready baseline: a flexible camera suite built from the original jitter-removal goal, now ready for real projects.

    

    

    Version 2.0 Development Trail In Progress
    

    

    
	Version 2.0 pushes the Dynamic Camera System further away from depending on Stencyl's built-in camera render path. The major focus is smoother camera movement, stronger multi-viewport rendering, and reducing repeated CPU/GPU work while keeping Stencyl as the editor and gameplay workflow.

    


    Cached Background Renderer - Implemented
    

      

    • bittyBIG now renders Stencyl background source frames through its own camera and floating-point parallax math instead of relying on Stencyl's pixel-snapped background position.
      • 

    • Background presentation data is reused per viewport while Stencyl continues to own source assets, animation timing, and scrolling state.
      • 

    • Result: smoother background movement and parallax that stays aligned with the bittyBIG camera.
      • 

    


    Cached Tile / World Renderer - Implemented
    

      

    • Static tile rendering now uses the shared BittyTileCache instead of asking Stencyl's tile layer to redraw separately for each camera.
      • 

    • Cached tile chunks are reused across camera captures while dynamic actors and drawing continue through the normal Stencyl world-layer display tree.
      • 

    • Result: less dependency on Stencyl's built-in camera and substantially less repeated static rendering work.
      • 

    


    Automatic Cache Refresh - Superseded Manual Rebuild Blocks
    

      

    • The originally planned manual rebuild blocks were not needed after the cache gained automatic change detection.
      • 

    • Tile changes, visual variants, source changes, and animated tile state are detected during cache synchronization and the affected cached content is refreshed automatically.
      • 

    • Result: users do not need to manually tell the camera system when normal tile content changes.
      • 

    


    Dirty-Region / Changed-Chunk Updates - Implemented
    

      

    • Changed tile cells update only their affected cached chunk instead of forcing the entire tile world to be rebuilt.
      • 

    • On the Windows GPU-first path, dirty chunks are refreshed and reusable GPU-side chunk images are retained.
      • 

    • Result: larger scenes and runtime tile edits require much less redundant work.
      • 

    


    Animated / Dynamic Background Support - Implemented
    

      

    • bittyBIG reads the current Stencyl background animation frame while preserving Stencyl's scrolling-background timing and independent scroll phase.
      • 

    • Repeating backgrounds, custom scroll factors, and parallax continue to work through the bittyBIG-controlled presentation path.
      • 

    • Result: animated and moving backgrounds retain smooth camera-controlled positioning instead of being limited to a static cache.
      • 

    


    HTML5 Tile Seam Improvements - Implemented
    

      

    • The shared tile-cache path avoids repeatedly rebuilding Stencyl's tile layer at different camera origins during the same frame.
      • 

    • The renderer uses expanded capture coverage / safety pixels where needed so smooth subpixel camera movement does not have to be snapped to hide seams.
      • 

    • Result: the previous one-pixel tile-phase seam path is avoided while keeping smooth camera movement.
      • 

    


    Renderer Independence - Major V2.0 Step Implemented
    

      

    • Static tiles and Stencyl backgrounds are now presented through bittyBIG-controlled camera/render paths instead of depending on Stencyl's camera transform for each viewport.
      • 

    • Stencyl remains responsible for the editor, actors, behaviors, scene setup, assets, animation state, and normal gameplay workflow.
      • 

    • Result: bittyBIG owns substantially more of the runtime camera/output behavior without requiring users to abandon Stencyl's creation pipeline.
      • 

    


    Scene-Centered Camera / Zoom-Aware Parallax - Implemented
    

      

    • Scene limiting now clamps the resolved camera center itself, so the camera's actual center stays authoritative at scene edges.
      • 

    • Background movement is calculated from the resolved camera center relative to the scene center, and Stencyl's stored scroll factor is converted to a zoom-aware effective factor so the same logical travel span is preserved as the visible camera size changes.
      • 

    • Smooth clamp-center presentation compensates for the parity-matched raster source sizes used during zoom.
      • 

    • Result: backgrounds stay aligned with the camera and scene edges through movement and smooth zoom without edge drift or clamp jitter.
      • 

    


    Background Repeat / Anchor Controls - Implemented
    

      

    • Background repeat can be overridden per layer as None, Horizontal, Vertical, or Both while leaving Stencyl's own Repeat setting untouched when no override is used.
      • 

    • Repeating backgrounds prepare only the minimum number of source copies needed for coverage; the previous extra safety copy is not added.
      • 

    • Background positional anchoring is stored per layer with normalized X/Y values from 0 to 1. Layers without an override default to 0,0.
      • 

    • Result: background preparation and registration are explicit per-layer controls without introducing another rendering path.
      • 

    


    Unified Rotation / Flip Presentation Path - Implemented
    

      

    • Rotation no longer switches to a separate capture bitmap, separate world renderer, or separate transformed-camera presentation path.
      • 

    • Ordered layers, backgrounds, zoom, scene clamping, parallax, and smoothing now run through the same normal rendering path first.
      • 

    • Rotation and flipping are applied only at the final presentation stage.
      • 

    • Result: rotation inherits the same rendering behavior and fixes as ordinary rendering and zoom instead of maintaining parallel special cases.
      • 

    


    Pixel-Aligned World Raster + Fractional Presentation Residual - Implemented
    

      

    • The rasterized world / tile camera origin is split into a pixel-aligned raster position and a fractional remainder.
      • 

    • The world is rendered at the stable pixel-aligned origin, while the fractional remainder is preserved and applied at final presentation.
      • 

    • Rasterized world layers with non-1.0 scroll factors are compensated so their parallax rate remains correct when the shared final residual is applied.
      • 

    • Result: the subtle main tile-layer shimmer is removed during ordinary camera movement and at the ends of zoom transitions while smooth fractional movement is preserved.
      •
